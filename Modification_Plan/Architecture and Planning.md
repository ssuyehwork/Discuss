# ArcMeta 架构与设计理念规范 (Architecture and Planning)

## 1. 全局数据引擎与内存模式架构规范

### 1.1 全局数据/内存管理面板 (Global Data & Memory Engine)

#### 1.1.1 500万+ 海量数据高性能全局架构重构规范

##### A. 内存模式下：
系统的全局标准规范严格按照以下【止血 → 提速 → 规范】三级优先级顺序执行：

1. **【第一优先级·止血】废除全量内存深拷贝**
   - **架构要求**：在 500 万+ 数据规模下（内存占用约 1.5GB - 2GB），严禁在单个元数据（如评分、标签、颜色、分类）更新时使用 `std::unordered_map` 的全量深拷贝（`make_shared<map>(*oldMap)`）。
   - **重构设计**：内存元数据镜像由单一整块哈希表升级为 **分块管理（Chunked Block Repository）或细粒度局部修改机制（Sharded Concurrent Map）**。修改单个属性耗时严格控制在 $O(1)$，不再复制全库，彻底根除 OOM 与垃圾回收（GC）引起的主线程冻结。

2. **【第二优先级·提速】改用增量记账与预烘焙指纹**
   - **架构要求**：严禁在 `StatisticsService` 侧边栏计数、`getAllTags()` 标签统计或任何高频事件中使用 `for` 循环全量遍历 500 万项节点，严禁在 UI 列表渲染过程中实时计算色差。
   - **重构设计**：
     - **增量账本**：侧边栏计数与系统统计全面采用增量账本（实时 $+1 / -1$ 原子变化），不再循环 500 万次扫描。
     - **预烘焙指纹**：颜色、尺寸与筛选标记在资产入库/修改时直接预先计算并烘焙为快速特征指纹。滚动列表视图（`filterAcceptsRow`）时实现 $0$ 浮点计算与纯布尔/位运算判断，确保列表滚动保持 60 帧满帧丝滑。

3. **【第三优先级·规范】确立单一事实源（SSOT）与管家类**
   - **架构要求**：彻底解耦资产元数据与分类关系，禁止在 `MetadataManager` 与 `CategoryRepo` 间出现交叉同步与两套账对账的补丁代码。
   - **重构设计**：分类与资产的所有绑定关系统一交由唯一的管家类（`CategoryBindingManager` / 专属资产关系引擎）集中管理，确立单一事实源（SSOT），彻底铲除两边打补丁对账的代码，保证系统职责单一与长期可维护性。

##### B. 磁盘目录模式下：
> *（注：磁盘目录模式 下的 内存模式500万+数据量高性能全局架构重构 逻辑架构尚未进行专题探讨与定义，暂时留空。）*


#### 1.1.2 500万+ 海量数据分阶段重构路线图规范

##### A. 内存模式下：
针对 500万+ 内存模式的全局重构，划分为 4 个独立递进的实施阶段（Stage 1 ~ Stage 4）：

1. **阶段一：底座止血阶段 —— 废除全量内存拷贝与容器升级**
   - **攻坚目标**：解决内存暴胀与频繁垃圾回收（GC）导致的主线程卡死与 OOM 崩溃。
   - **实现规范**：彻底废除 `MetadataManager` 中的全量 COW 拷贝模式，引入分片并发哈希容器（Sharded Concurrent Map）或分块内存池（Chunked Block Repository）。局部更新耗时控制在 $O(1)$，分配额外内存为 $0$。
   - **验收标准**：500 万数据规模下修改任意元数据，内存零增长，更新耗时 $\le 1\text{ms}$。

2. **阶段二：提速引擎阶段 —— 增量账本与内存倒排索引**
   - **攻坚目标**：消除全库 O(N) 线性遍历，实现侧边栏统计与分类筛选瞬时响应。
   - **实现规范**：将 `StatisticsService` 重构为纯增量账本引擎（Incremental Ledger Engine），资产变更实时原子 $+1 / -1$；建立并维护标签与分类的内存倒排索引（Inverted Indexing），分类/标签检索通过集合运算完成。
   - **验收标准**：切换分类或侧边栏出账时 CPU 占用不飙升，计算耗时 $\le 5\text{ms}$。

3. **阶段三：渲染预烘焙阶段 —— UI 零计算与丝滑滚动**
   - **攻坚目标**：消除 UI 过滤代理层的高频计算，保障 500 万数据视图滚动 60 FPS。
   - **实现规范**：引入元数据预烘焙指纹机制（Metadata Baking Stage），在资产入库/修改阶段预先算好色差与特征位；重构 `FilterProxyModel::filterAcceptsRow`，全量替换为纯按位与/布尔匹配。
   - **验收标准**：快速拖拽列表滚动条时 `filterAcceptsRow` 单次耗时 $< 0.1\mu\text{s}$，帧率稳定在 60 FPS。

4. **阶段四：SSOT 治理阶段 —— 资产关系集中化与补丁清理**
   - **攻坚目标**：确立单一事实源（SSOT），彻底铲除两套账与打补丁对账代码。
   - **实现规范**：创建专职的资产关系管家引擎（`CategoryBindingManager`），统一托管资产与分类的绑定、解绑与持久化，清理 `MetadataManager` 与 `CategoryRepo` 中的对账 SQL 与僵尸代码（包含对齐与清除 `CategoryLoadService.cpp` 中绕过数据库匹配路径的 SCCH 遗留逻辑）。
   - **验收标准**：分类映射逻辑单一收拢，无对账补丁，单元测试 100% 覆盖。

##### B. 磁盘目录模式下：

#### 1.1.3 500万+ 阶段一底座止血具体技术实现规范 (MetadataManager 分片容器架构)

##### A. 内存模式下：
1. **256 分片并发容器结构设计 (256-Sharded Concurrent Map)**
   - **架构定义**：`MetadataManager` 底层采用 `std::array<MetaShard, 256>`，其中每个 `MetaShard` 包含独立的 `std::shared_mutex` 和 `std::unordered_map<std::wstring, RuntimeMeta>`。
   - **分片路由算法**：单项路径通过 `std::hash<std::wstring>{}(path) % 256` 确定归属分片，锁冲突概率严格稀释至 $1/256$。

2. **单项元数据写操作规范 (setRating / setTags / setColor)**
   - **加锁规范**：排他更新时仅获取目标分片 `m_shards[shardIndex].mutex` 的 `std::unique_lock`，严禁锁住全局或调用任何全量深拷贝函数。
   - **性能指标**：单次写更新时间复杂度 $O(1)$，耗时 $< 0.01\text{ms}$，分配额外内存为 $0$。

3. **并发读与批量写安全锁顺序规范**
   - **读操作 (getMeta)**：仅获取目标分片的 `std::shared_lock`，支持多线程跨分片高并发只读。
   - **批量跨分片写 (renameBatchAsync / removeMetadataBatchSync)**：涉及到跨分片更新时，必须先将路径列表按 `shardIndex` 升序排列，并按升序依次加锁，彻底规避死锁。

##### B. 磁盘目录模式下：

#### 1.1.4 RCU快照模式 → 256分片模式 迁移一致性规范

##### A. 内存模式下：

**背景**：现行 `MetadataManager` 采用 RCU 快照模式（`atomic_load`/`atomic_store` 整块 `map` 指针切换），写操作本质是 `make_shared<map>(*oldMap)` 全量深拷贝，正是 1.1.1 第1点点名严禁的模式。256分片架构（1.1.3）是对RCU模式的**替换**，而非并行共存方案。

1. **`forEachCachedItem()` 一致性承诺降级规范**
   - **架构要求**：迁移至256分片后，`forEachCachedItem()` 全表遍历严禁退回"全量加锁遍历"，必须改为**弱一致性遍历**——逐分片依次获取该分片 `shared_lock` 读取、读毕立即释放再进入下一分片，不提供跨分片的原子快照保证。
   - **适用范围声明**：以下消费者已确认可接受弱一致性，不需额外补偿逻辑，任何新增的全表遍历消费者必须比照此标准评估，不得擅自要求恢复强一致性快照：
     - `StatisticsService::computeSnapshotFromDb()`（全量重算校准，允许极小误差，下次增量账本自我修正）
     - `DuplicateDetectorService::detectDuplicates()`（允许扫描期间极小概率漏检/误检并发修改中的记录，重新导入可再次检测）
     - `CategoryModel` 刷新路径（UI展示允许短暂"最终一致"）

##### B. 磁盘目录模式下：
> *（注：磁盘目录模式 下的 RCU快照模式 → 256分片模式 迁移一致性规范 逻辑架构尚未进行专题探讨与定义，暂时留空。）*


#### 1.1.5 全局跨类加锁顺序总规范

##### A. 内存模式下：

**架构要求**：1.1.3 第3点"批量跨分片写按 shardIndex 升序加锁"仅约束 `MetadataManager` 内部256分片间的加锁顺序，**不覆盖跨类加锁场景**。项目中任何函数如需**同时**持有 `DatabaseManager` 与 `MetadataManager` 的锁，一律按以下全局总顺序获取，严禁任何函数以相反顺序加锁：

```
第一顺位：DatabaseManager per-drive 锁
第二顺位：MetadataManager shard 锁
```

此规则为全项目强制总纲，优先于任何局部模块内部的加锁顺序规则；新增涉及双锁的函数必须先对照本条校验顺序，禁止各自为政。

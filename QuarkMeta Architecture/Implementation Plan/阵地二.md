### 一、 事实：当前元数据存储底座的核心现状

`MetadataManager` 是整个软件的“元数据心脏”，目前它承担了以下 4 大底层交互：

1. **混合存储模式（双轨持久化）**：
   - **轨道 A（分布式本地文件）**：每个物理文件夹下的 `.QuarkMeta.json`，负责记录该目录下所有文件的星级、颜色、标签、备注、宽高与色板；
   - **轨道 B（全局集中数据库）**：SQLite `global.db`，负责存储驱动器卷标元数据（`DriveMetaDao`）、全局词库（`TagRepository`）与回收站映射（`DiskTrashRepo`）。
2. **高频小 I/O 写盘风险（Write Thrashing）**：
   - 当用户在同一个目录下批量修改 100 个文件的星级或尺寸时，每次调用 `setRating` 都会实例化 `QuarkMetaJson`、执行 `load()`、修改 1 个项、再执行 `save()`；
   - 导致该目录下的 `.QuarkMeta.json` 在 1 秒内被**反复打开、序列化、写入磁盘达 100 次**！
3. **`MetadataManager` 上帝门面膨胀**：
   - 一个类中混合了 Win32 底层 API（`fetchWinApiMetadataDirect`）、JSON 读写锁（`s_jsonSaveMutex`）、LRU 内存缓存（`RuntimeMetaCache`）、SQLite 数据库事务以及批处理改名索引同步（`renameBatchAsync`）。

---

### 二、 推断：现有存储底座的 2 大性能隐患（因果链路）

- **[推断 1 - 高频批量写盘导致磁盘 I/O 剧烈抖动]**
  - **原因**：`QuarkMetaJson` 缺乏“脏数据缓冲与聚合刷盘机制（Dirty Buffer Flush）”。
  - **影响**：只要发生批量打标、批量改色或尺寸预提取，相同的 JSON 文件被疯狂重复写入数百次。
  - **结果**：造成机械硬盘剧烈寻道发热，甚至在网络共享盘（NAS）或慢速 U 盘上引发写文件锁冲突与假死。
  - **标准解法**：引入 **`beginInternalOperation() / endInternalOperation()` 事务合并机制**——在批量操作期间，内存中合并修改，退出操作锁时**仅执行 1 次最终物理写盘**。

- **[推断 2 - 门面类职责过重导致存储引擎与缓存耦合]**
  - **原因**：`MetadataManager` 直接包含了文件 I/O 细节与缓存淘汰算法。
  - **影响**：一旦需要优化 JSON 序列化性能（如引入 RapidJSON 或 SIMD-JSON）或者调整 LRU 缓存大小，必须大幅修改整个核心管理器。
  - **结果**：违背了开闭原则（OCP）。

### 三、 阵地二的归一化架构治理蓝图

```
                         【元数据持久化底座标准架构】

    ┌─────────────────────────────────────────────────────────────────────────────┐
    │       MetadataManager (对外统一门面 - Facade，纯粹调度，0 I/O 杂质)         │
    ├─────────────────────────────────────────────────────────────────────────────┤
    │ • 统一查询：getMeta(path) ──► 先查一级内存 Cache ──► 未命中查磁盘 JSON/DB  │

    └──────────────────────────────────────┬──────────────────────────────────────┘
                                           │ (分工明确的三大底层子模块)
        ┌──────────────────────────────────┼──────────────────────────────────┐
        ▼                                  ▼                                  ▼
【 MetaMemoryCache 】             【 QuarkMetaJsonStore 】           【 MetaDbRepository 】
```

1. **实现 100 次修改只写 1 次磁盘**：在 `MetadataManager` 中引入批量脏块合并机制，彻底消灭高频重复写盘对硬盘的损耗；

### 一、 事实：当前存储底座的代码现状与设计亮点

审查发现，存储底座在前期重构中已经具备了良好的**分层雏形**与**原子安全写盘机制**：

1. **原子替换写盘与断电安全防护（优秀设计）**：
   在 `QuarkMetaJson::save`（第 61~89 行）中：
   - 写入临时文件 `.QuarkMeta.json.tmp`；
   - 使用 Win32 API `MoveFileExW(..., MOVEFILE_REPLACE_EXISTING)` 进行**原子物理替换**；
   - 自动赋予 `FILE_ATTRIBUTE_HIDDEN` 隐藏属性。
   - **该机制能 100% 避免因断电或强杀进程导致原 `.QuarkMeta.json` 被截断写坏。**
2. **UI 信号 200ms 聚合防抖（优秀设计）**：
   `MetadataManager` 内置了 `m_uiSignalTimer`（200ms 防抖单触发），当变更路径大于 50 项时自动合并为单次 `__RELOAD_ALL__` 广播，有效抑制了前端事件风暴。
3. **单项写入与磁盘 I/O 放大隐患（需加固）**：
   在 `setRating`、`setColor`、`setTags`、`setNote`、`setURL` 中，每次调用都同步触发了 `QuarkMetaJsonStore::updateItemMeta`。
   - 若外部循环修改同一个文件夹下的 100 个文件，如果调用方忘记显式加 `beginInternalOperation()` 锁，该目录的 JSON 将被**同步反复读取、JSON 解析并写入磁盘 100 次**。
4. **存在工具代码重复**：
   `MetadataManager::getVolumeSerialNumber` 与 `VolumePathResolver::getVolumeSerialNumber` 两处代码完全一模一样，存在冗余重复。

---

### 二、 推断：现有设计的性能瓶颈（因果链路）

- **[推断 1 - 依赖外部手动加锁容易导致防抖失效与 I/O 放大]**
  - **原因**：目前防重复写盘的机制依赖调用方必须记得调用 `beginInternalOperation() / endInternalOperation()`。
  - **影响**：一旦未来有新的开发者、新的 Service（如批量特征提取、后台提色）或者外部脚本直接循环调用 `setRating` 且漏掉了手动加锁。
  - **结果**：系统瞬间退化为“每改一个属性就写一次硬盘”的高频 I/O 震荡模式，在慢速机械硬盘或 NAS 网络驱动器上引发明显卡顿。
  - **标准解法**：在 `QuarkMetaJsonStore` 底层内置**“脏目录缓冲合并（Dirty Directory Flush）”**——同一事件循环（或 50ms 内）对同目录的多次修改，底层自动合并，退出时只写 1 次磁盘。

- **[推断 2 - Win32 杂质依然残留于门面类]**
  - **原因**：`fetchWinApiMetadataDirect`（`CreateFileW`、`GetFileInformationByHandle`）直接以内联形式写在 `MetadataManager.cpp` 内部。
  - **影响**：导致 `MetadataManager` 依然掺杂了底层文件系统的 Win32 API 调用。
  - **结果**：应将其下沉至 `src/util/FileOperationHelper` 或 `DiskIoService`，使 `MetadataManager` 彻底脱敏为纯粹的门面路由。

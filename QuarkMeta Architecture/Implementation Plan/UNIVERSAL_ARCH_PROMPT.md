## 🛑 第一部分：架构绝对红线（违反即判为失败）

1. **【严禁盲改对外签名（Public API Freezing）】**
   - 严禁随意修改已有的 public 函数名称、参数列表、返回值类型及默认实参。
   - 当需要扩展功能时，采用「函数重载」、「添加默认参数」或「引入扩展结构体」，绝对不允许破坏既有调用方的编译契约。

2. **【严禁伪解耦与友元侵入（No Friend Classes）】**
   - 严禁为了访问私有成员而声明 `friend class`。
   - 任何拆分出的 Controller、Mediator、Helper 均不得持有上帝类的裸指针并直接读写其私有字段。
   - 模块间通信**只能通过标准接口、标准信号槽（Signals/Slots）或明确的 DTO 实体**进行。

3. **【严禁平台 Hack 级补丁（Zero Patch Tolerance）】**
   - 严禁在未查明根因的情况下，随意引入操作系统底层 API（如 Win32 `SetForegroundWindow`、消息截获）来“暴力掩盖”上层焦点、激活或生命周期问题。
   - 严禁在样式/渲染工具类（如 SvgRenderer/UiHelper）中篡改控件的顶层窗口标志（如 `setWindowFlag(Qt::FramelessWindowHint)`）导致原生事件链断裂。

4. **【严禁 Model-View 抽象穿透】**
   - 严禁在 View 外部或 Mediator 中将 `QAbstractItemModel` 强转为具体模型类并直接遍历其内部 `private` 数据容器。
   - 数据获取必须严格通过标准 `model->data(index, role)` 协议进行。

5. **【严禁批量循环发射事件（防止事件风暴）】**
   - 在处理 $N$ 个项目的批量操作（星级、颜色、标签、删除等）时，严禁在 `for` 循环内逐个发射全局事件。
   - 必须先完成全量数据操作，最后只发射 1 次聚合批量事件（携带完整的 `paths` 列表）。

## 🔧 第三部分：标准重构执行步骤（每次行动必须遵守）

当你面对臃肿类（上帝类）或复杂 Bug 时，必须按以下步骤展开工作：

### 步骤 1：根因定位（Root-Cause Analysis）
- 找出问题的真实源头（是窗口标志冲突？焦点竞争？生命周期越权？还是数据模型未同步？）。
- 绝不使用局部 Workaround 来压制表象。

### 步骤 2：契约冻结（Contract Freezing）
- 审查涉及的公开头文件，列出所有被外部调用的接口，确保本次修改不对其签名产生破坏。

### 步骤 3：单向依赖拆分（Unidirectional Decoupling）
- 如果上帝类（如 `MainWindow`）过大：
  1. 将无边框拖拽/拉伸逻辑抽离为独立的 `FramelessWindowHelper`（通过事件过滤器生效）。
  2. 将导航历史栈与当前路径抽离为独立的 `NavigationService` 单例。
  3. 将右键菜单的 Action 构建与响应抽离为 `ContextMenuHandler`。
- 上帝类仅负责顶层组装，代码行数应收敛为纯装配逻辑。

### 步骤 4：编译与副作用检查（Side-Effect Verification）
- 检查是否有因修改类型导致的隐式类型截断、静默失败。
- 确保所有批量操作的 UI 刷新是 $O(1)$ 次数的聚合刷新，而非 $O(N)$ 的高频刷新。

### 一、 为什么“不写大纲直接写代码”必死无疑？

如果不先定大纲，开发者或 AI 在写代码时就只有**“局部视野”**：
1. **写 UI 时顺手塞业务**：在 `MainWindow` 里随手加了个路径跳转，下次加个历史记录，再加个右键菜单……不知不觉写出了 2000 行的上帝类。
2. **写控制器时顺手改底层**：发现某个参数传不过去，就顺手去改底层接口的签名，导致其他 10 个文件瞬间报错，然后到处打补丁。
3. **遇到 Bug 时暴力掩盖**：发现右键菜单弹不出，根本不知道焦点链在哪一层，只能在最外层加一个 `SetForegroundWindow` 的 Win32 补丁。

**没有大纲的代码开发，本质上就是在“没有施工图纸的情况下盖大楼”，地基没打好，上面多盖一层就歪一层，最后只能靠无数根烂木头（补丁）到处乱顶。**

---

### 二、 正规的应用开发大纲必须包含哪 5 大要素？

一个合格的应用开发大纲（Architecture Blueprint）绝对不是简单的“功能列表（ToDo List）”，而是以下 5 个维度的**契约与边界定义**：

```
┌─────────────────────────────────────────────────────────────┐
│                   正规应用开发大纲 (5 维图谱)                   │
├───────────────────┬─────────────────────────────────────────┤
│ 1. 状态持有大纲    │ 每一个全局状态（路径/选中项/配置）到底归谁管？  │
├───────────────────┼─────────────────────────────────────────┤
│ 2. 数据流动大纲    │ 数据从磁盘 -> 内存 -> Model -> UI 的单向流向 │
├───────────────────┼─────────────────────────────────────────┤
│ 3. 接口契约大纲    │ 模块之间的 Signal/Slot/Command 参数严格冻结  │
├───────────────────┼─────────────────────────────────────────┤
│ 4. 线程与并发大纲  │ 哪些操作绝对不准在 UI 主线程执行？             │
├───────────────────┼─────────────────────────────────────────┤
│ 5. 模块生命周期大纲│ 启动顺序、托盘常驻、退出拦截（CloseEvent）流程 │
└───────────────────┴─────────────────────────────────────────┘
```

#### 1. 状态持有大纲（Single Source of Truth，唯一真理源）
- **错误做法**：`MainWindow` 存一份路径，`ContentPanel` 存一份路径，`AddressBar` 又存一份路径，三者互相同步，死循环。
- **大纲规定**：全系统**只有 `NavigationService`** 允许持有 `currentPath` 和 `historyStack`，其他所有 UI 只能作为观察者（Observer）监听变化。

#### 2. 数据流动大纲（单向数据流）
- **大纲规定**：
  - 用户操作 UI -> 发射 `AppCommand` -> `CoreEngine` 校验并执行 -> 触发底层写入 -> 发射 `AppEvent` -> `Model` 更新 -> `View` 重新绘制。
  - **严禁逆向流动**（如：UI 控件直接越过 Engine 跑去改 SQLite 数据库或修改其他 Panel 的私有数据）。

#### 3. 接口契约大纲（Interface Contract）
- 在写任何业务之前，先把公共的 `.h` 头文件、枚举（`AppCommandType`、`AppEventType`）、结构体（`ItemRecord`）定死并**冻结（Freeze）**。
- 后续开发只能在 `.cpp` 里写实现，**任何人在没有经过架构评审前，不准随意修改 `.h` 里的公共函数签名**。

#### 4. 线程与并发大纲（Threading Boundary）
- **大纲规定**：
  - UI 线程：仅负责组件装配、PaintEvent 绘制、用户输入捕获。
  - 后台线程池：文件扫描、元数据提取（Extractor）、缩略图生成、SQLite 批量落盘。
  - 严禁在主线程调用耗时超过 5ms 的同步文件 IO。

#### 5. 生命周期大纲（Lifecycle Rules）
- 明确应用从 `main.cpp` -> 数据库连接 -> 核心服务预热 -> 主窗口展示 -> 最小化到托盘 -> 真正退出的全生命周期流程，杜绝在局部子模块中私自调用 `QApplication::exit(0)`。

### 三、 正规开发的 4 步标准化落地流程

无论是团队协作，还是指挥 AI（如 Jules）写代码，必须严格执行以下 4 步：

```
第 1 步：出具《架构大纲与分层设计》（确定谁负责什么，谁不准碰什么）
   │
   ▼
第 2 步：冻结《核心数据结构与接口契约》（把 .h 文件和枚举先定义好，禁止再动签名）
   │
   ▼
第 3 步：搭建《骨架与信号管道》（类与类之间用空函数连接，跑通通讯流程）
   │
   ▼
第 4 步：填充《业务细节与单元实现》（逐个模块写 cpp 实现，有 Bug 只在模块内修，绝不扩散）
```

## 🎯 核心原则与架构红线

你在审计当前代码库与制定大纲时，必须无条件遵循以下**【四大架构铁律】**：

1. **【严禁盲改对外签名（Public API Freezing）】**
   - 严禁随意修改已有的 Public 函数名、参数列表、返回值类型及默认参数。
   - 当需要扩展或重构时，必须保证既有调用方的编译兼容性，杜绝因修改底层接口而导致全工程数十个文件级联报错的现象。

2. **【严禁伪解耦与友元侵入（No Friend Class Invasions）】**
   - 严禁为了“拆分文件”而将上帝类的私有成员直接暴露给外部类或使用 `friend` 关键字。
   - 任何拆分出的辅助类、协调器均不得持有容器类的裸指针去直接读写私有字段。模块间必须通过标准接口、强类型数据契约或事件总线单向通信。

3. **【严禁平台级 Hack 补丁（Zero Patch Tolerance）】**
   - 严禁在未查明根因的情况下，引入操作系统底层原生 API（如暴力夺焦、强制注入、重置窗口标志）来掩盖上层逻辑漏洞。
   - 严禁在样式、渲染或通用工具类中附带具有破坏性的窗口行为副作用。

4. **【严禁状态多头持有（Single Source of Truth, SSOT）】**
   - 每一个业务状态（如当前路径、历史记录、选中项、全局配置）在全系统中必须且只能有**一个唯一的持有与管理者（Service/Store）**，UI 控件与其他模块只能作为观察者（Observer）或通过命令（Command）请求修改，严禁多处存储、多向同步。

## 📋 必须输出的标准大纲结构

### 1. 系统标准五层架构拓扑大纲 (Layered Architecture Mapping)
梳理当前仓库中所有核心类与模块，将其严格划归至以下五层架构中，明确定义每一层的职责与禁止行为：
- **第一层：外壳与平台交互层 (Shell / Native Layer)**（仅负责操作系统级窗口行为、底层设备/硬件事件监听，无任何业务逻辑）
- **第二层：视图与呈现层 (View / Presentation Layer)**（纯 UI 控件布局、视觉渲染与用户交互捕获，内部状态严格封装为 private）
- **第三层：路由与协调层 (Mediator / Coordinator / Handlers)**（纯事件路由与动作分发，严禁包含 UI 排版与底层文件/数据库 IO）
- **第四层：业务领域层 (Domain Service / Core Engine)**（全局业务状态唯一持有者，负责命令合法性校验、事务调度与聚合事件分发）
- **第五层：数据与持久化层 (Repository / Data Access Layer)**（负责数据库、本地文件、配置的物理读写，耗时 IO 必须与主线程完全隔离）

### 3. 数据契约与事件流动规范 (Data Contract & Anti-Storm Rules)
- **输入流 (Command Pipeline)**：定义 UI 发起操作至领域层处理的单向请求契约，禁止 View 越权直接操作 Repository。
- **输出流 (Event Pipeline & 批处理防风暴)**：
  - 明确禁止在处理批量数据时于循环内部逐个触发全量广播；
  - 强制规定批量操作必须在数据持久化完成后，仅发射 1 次聚合批量事件（携带完整的实体列表/路径集合）。
- **Model-View 访问契约**：严格禁止 View 层或 Mediator 强转 Model 指针直接访问私有内存容器，必须统一通过标准数据角色（Role/Data API）读取。

### 4. 上帝类与高耦合模块拆解规划 (God-Class Decomposition Plan)
针对当前代码库中代码量过大（>500行）、包含多重职责的“上帝类”列出详细拆分方案：
- **列出识别出的上帝类及其当前承担的杂乱职责**；
- **职责剥离方案**：说明将哪些具体职责（如窗口拖拽、右键菜单响应、文件操作、历史栈管理）剥离至哪些新命名的独立类中；
- **解耦方式**：说明如何通过标准信号槽/接口完成连接，且保证不引入 `friend class`。

### 5. 契约冻结与向后兼容清单 (Public API Freeze List)

- 阐述如何做到在完全不改变外部调用代码的前提下，平滑替换其内部底层实现。

### 6. 无损分阶段重构实施路线图 (Phased Implementation Roadmap)
制定小步快跑、分阶段落地的实施计划，确保**每一个阶段提交后，项目均处于可编译、可运行、无回归错误的状态**：

### 推断：

- **[推断 1 - 职责定义虚化导致的二次上帝类风险]**
  - **原因**：文档第 2 节对 60 多个 UI 类采用了完全相同的占位模板文本，没有明确每个 UI 组件属于“容器组件（Container）”还是“受控展示组件（Presentational）”，亦未界定各个 Dialog/Panel 与底层 Service 之间的数据获取界限。
  - **影响**：AI 或开发人员在根据此大纲落地代码时，依然无法获知具体 UI 控件（如 `QuickLookWindow`、`TagManagerDialog`）该从哪里拿数据、能否直接调用 `CoreEngine`。
  - **结果**：极易导致开发者在具体的 UI 文件中继续塞入业务 IO 或再次通过 `friend` 侵入其他类，未能从根源上杜绝上帝组件的再生。

- **[推断 2 - 顶层大纲与视觉规范混杂导致的规范腐化]**
  - **原因**：大纲中混入了大量“7 秒 Toast”、“230px 边栏宽度”、“1px border-left 分隔线”等纯 UI 表现层参数，违反了文档自身的“纯洁性保护红线”。
  - **影响**：将高变动性的视觉样式（Styling）与高稳定性的系统拓扑架构（Architecture）耦合在同一个顶层大纲中。
  - **结果**：未来任何一次 UI 视觉微调都会导致系统架构大纲被频繁修改，降低了架构文档的权威性与稳定性。

- **[推断 3 - 托盘硬杀逻辑仍存线程安全截断隐患]**
  - **原因**：大纲规定托盘退出必须调用 `exit(0)` 强退主事件循环。
  - **影响**：当后台 `QtConcurrent` 正在进行大文件 SHA-256 哈希计算或 SQLite 事务正在提交时，强退事件循环可能导致正在执行的底层清理序列（`aboutToQuit`）得不到充分的堆栈展开与资源安全析构。
  - **结果**：在低概率并发场景下可能导致数据库 WAL 日志锁死或异常退出。

### 重构建议（大纲完善方案）：

#### 1. 消除第 2 节的“占位式模板文本”，按子系统聚合定义真实边界
不要给每一个 UI 文件复制相同的“处理自绘与用户事件”，建议按**子系统（Subsystem）**明确数据流向：
- **预览子系统（QuickLook 体系）**：`QuickLookWindow` 仅负责展示，数据统一由 `DiskItemModel` 经由结构体注入，严禁在预览窗口中直接操作文件系统。
- **对话框体系（FramelessDialog 体系）**：统一下沉为标准模态输入框，仅通过 `QDialog::Accepted` 与返回值与调用方通信，严禁在 Dialog 内部耦合全局中控。

#### 2. 将视觉度量参数剥离至独立的《UI 视觉与设计规范》
- 将 230px、7000ms、1px 边框、特定十六进制颜色等具体设计参数抽离至 `UI_DESIGN_SPEC.md`。
- 本架构规划文档只保留：**五层架构分层原则、状态持有者唯一性（SSOT）、Model-View 数据获取契约、并发与线程隔离策略**等核心架构骨架。

#### 3. 规范托盘退出协议为标准退出流
- 托盘控制器只需发射 `quitRequested` 或调用 `qApp->closeAllWindows()`；
- 由主窗口统一在 `closeEvent` 中调度后台任务停止与落盘，最后由 Qt 自身主流程安全退出，移除要求强制 `exit(0)` 的顶层约束。

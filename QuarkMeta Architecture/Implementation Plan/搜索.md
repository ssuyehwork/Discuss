### 一、 事实：当前搜索与筛选体系的代码现状

分析 `ContentPanel.cpp`、`FilterPanel` 及 `CoreController` 的现有逻辑，发现当前系统包含两套性质不同的数据通道：

1. **通道一：当前目录“即时内存过滤”（Local Instant Filter）**：
   - 用户在搜索框打字时，`SearchController` 调用 `ContentPanel::search(query)`；
   - 内部将 `m_currentFilter.keyword = query`，直接通过 `FilterProxyModel` 在主线程内存中对当前已加载的列表进行文件名、标签、备注的模糊匹配；
   - 耗时 $< 1\text{ms}$，不发生任何磁盘 I/O。
2. **通道二：跨目录/全局“深度磁盘搜索”（Deep Disk Search）**：
   - 调用 `CoreController::performSearch` 启动 `PhysicalDiskSearchExtractor`；
   - 在后台子线程遍历目录树，通过 `CoreController::searchResultsAvailable` 信号分批次向 `ContentPanel::appendPaths` 流式追加路径；
   - 内容面板切换为 `DataSourceType::PathList`（临时列表模式）。
3. **通道三：右侧多维条件筛选（FilterPanel Facet Filter）**：
   - 包含 11 个维度的复合过滤（星级、颜色、文件类型、创建/修改日期、备注、链接、文件大小、图像比例、缩略图状态、重复状态）；
   - `FilterPanel` 发射 `filterChanged(FilterState)` 信号通知 `ContentPanel` 重新过滤。
4. **防御性补丁代码的存在**：
   在 `ContentPanel::applyFilters(const FilterState& state)` 中，为了防止右侧筛选栏的默认配置覆盖顶部标题栏的“隐藏文件夹/隐藏文件”按钮状态，手写了变量备份与还原补丁：
   ```cpp
   bool preservedShowFolders = m_currentFilter.showFolders; // 👈 补丁：防被覆盖
   m_currentFilter = state;
   m_currentFilter.showFolders = preservedShowFolders;      // 👈 补丁：强行还原
   ```

### 二、 推断：现有设计的 3 大架构缺陷（因果链路）

- **[推断 1 - 标题栏按钮与右侧筛选栏“状态竞争与互踩”]**
  - **原因**：顶部标题栏的“显示/隐藏文件夹按钮”与右侧 `FilterPanel` 的“类型复选框”都在控制 `FilterState` 的过滤行为，但两者的状态源头没有统一。
  - **影响**：每次 `FilterPanel` 触发过滤时，都会把默认的全量状态下发给 `ContentPanel`，导致 `ContentPanel` 不得不写补丁代码去拦截覆盖。
  - **结果**：当后续增加新的顶部状态按钮（如“仅显示图像”）时，状态互踩问题会进一步恶化。

- **[推断 2 - `FilterProxyModel` 严重越权内嵌在 `ContentPanel` 中]**
  - **原因**：负责复杂 11 维过滤与置顶加权排序的 `FilterProxyModel`（近 300 行代码），被直接塞在 `ContentPanel.h` 与 `ContentPanel.cpp` 文件的最顶部。
  - **影响**：破坏了 Qt 标准 Model-View 的分层隔离，导致 `ContentPanel` 承担了视图容器、代理模型过滤、排序权重仲裁三重视图职责。
  - **结果**：内容面板文件体积庞大，过滤与排序算法无法被独立单元测试。

- **[推断 3 - 异步深度搜索结果的“代际竞争与过期污染”]**
  - **原因**：当后台 `PhysicalDiskSearchExtractor` 正在执行深层递归遍历并流式追加数据时，如果用户突然切换了目录或发起了新的搜索。
  - **影响**：前一次搜索的后台线程若未被瞬间硬熔断，会继续向主线程发射残留结果。
  - **结果**：导致旧的搜索结果混入新目录或新搜索结果中，造成界面内容乱跳与数据污染。

### 三、 探讨焦点：正规的搜索与多维筛选流体系应该如何设计？

一个工业级的搜索与筛选子系统，应当确立以下 **3 大标准化管道**：

```
                             【搜索与多维筛选统一架构】

   1. 统一筛选状态仓 (FilterStateStore / FilterStateModel)
   ──────────────────────────────────────────────────────────────────
   • 唯一持有 FilterState (合并了：关键词 + 标题栏显隐按钮 + 右侧 11 维筛选条件)
   • 任何一处修改（打字/点复选框/切按钮），统一更新 Store 并单向广播 `filterChanged`

   2. 独立代理模型 (src/ui/models/FilterProxyModel.h / .cpp)
   ──────────────────────────────────────────────────────────────────
   • 从 ContentPanel 中彻底抽离出来，下沉到 `src/ui/models/` 目录
   • 纯粹接收 FilterState，执行内存 O(1) 过滤与置顶优先排序

   3. 双模搜索明确分流 (Two-Mode Search Pipeline)
   ──────────────────────────────────────────────────────────────────
   • 模式 A (即时过滤): 用户在输入框打字 -> 直接更新 FilterState.keyword (纯内存 0ms 过滤当前视图)
   • 模式 B (深度搜索): 用户按回车/点全盘搜索 -> 生成新 generationId，彻底中断上一代任务 -> 异步流式输出
```

1. **状态源归一化**：建立统一的筛选状态管理，彻底消灭 `ContentPanel` 中为了防覆盖而写的 `preservedShowFolders` 补丁代码；
2. **模型抽离**：将 `FilterProxyModel` 独立为单独文件，使 `ContentPanel` 回归纯粹的 View 容器；
3. **代际熔断**：深度搜索通过原子代际号（`generationId`）实现毫秒级即时熔断，杜绝过期数据污染。

### 二、 推断：现有设计的系统性缺陷（因果链路）

- **[推断 1 - 状态多头持有导致搜索与筛选互相踩踏覆盖]**
  - **原因**：搜索关键词归 `SearchController` 管，11 维属性归 `FilterPanel` 管，标题栏显隐归 `ContentPanel` 管。

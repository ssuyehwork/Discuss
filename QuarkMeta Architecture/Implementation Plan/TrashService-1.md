# 移入回收站（删除） —— TrashService

**核心原则完全正确，但更严谨的表述是：“一个独立的业务领域（Domain Capability），对应一个独立的业务模块（Service）”。**

这正是软件工程中最核心的 **单一职责原则（Single Responsibility Principle, SRP）** —— **“一个模块应该有且仅有一个引起它变化的原因。”**

---

### 一、 什么样的功能“必须”独立成专属模块？（4 大黄金判断标准）

并不是每个按钮都要写个类，但如果一个功能满足以下 **4 个特征中的任意 2 个**，它就**必须**做成独立的单例/领域服务（Service）：

```
                       【必须独立模块化的 4 大判定准则】
┌─────────────────────────┬────────────────────────────────────────────────────────┐
│ 1. 改变的原因完全不同    │ 比如：软删除（因回收站策略改动）与硬删除（因安全粉碎算法改动）│
├─────────────────────────┼────────────────────────────────────────────────────────┤
│ 2. 状态与生命周期不同    │ 比如：可撤销的事务（需录制快照）与不可撤销的物理擦除（需清洗撤销栈）│
├─────────────────────────┼────────────────────────────────────────────────────────┤
│ 3. 存在多处 UI 入口复用 │ 比如：快捷键、右键菜单、预览窗口、重复文件清理对话框都要调用它│
├─────────────────────────┼────────────────────────────────────────────────────────┤
│ 4. 包含重型异步横切关注点│ 比如：涉及后台线程池、进度条弹出、元数据并发加锁、全局事件广播│
└─────────────────────────┴────────────────────────────────────────────────────────┘
```

---

### 二、 推断：两个极端的架构灾难（因果链路）

在模块化划分时，必须警惕两个极端：

- **[推断 1 - 极端 A：过度聚合（全部揉在一起，制造上帝类）]**
  - **原因**：把复制、剪切、软删除、硬删除、打标签、设评级全部写进 `ContentPanel.cpp` 或 `MainWindow.cpp`。
  - **影响**：代码量迅速膨胀至数千行，UI 控件深度依赖数据库、底层 I/O 与线程池。
  - **结果**：一个地方改坏（如前面修补表头），整个面板的删除、重命名全部跟着受牵连瘫痪。

- **[推断 2 - 极端 B：过度细碎（一个按键一个类，造成模块爆炸）]**
  - **原因**：把毫无异步逻辑、仅有一两行代码的简单动作也拆成类（如专门建一个 `OpenFolderService`、`CopyPathService`）。
  - **影响**：系统内部充斥着数百个微小类，类与类之间指针传递极其繁琐，代码结构支离破碎。
  - **结果**：增加了调用链层级，降低了代码阅读与调试效率。

### 三、 QuarkMeta 核心业务的“标准功能-模块映射大纲”

按照“正规、规范、标准”的架构，整个系统的业务功能应该收敛为以下 **7 个边界清晰的领域服务模块**：

| 功能范畴 | 专属独立模块 (Service) | 职责边界（只管什么） | 禁止做的事情（不准管什么） |
| :--- | :--- | :--- | :--- |
| **路径导航与历史** | `NavigationService` | 唯一持有当前路径、前进/后退历史栈 | 严禁写任何 UI 绘制与按钮 QSS |
| **普通删除（软删除）** | `TrashService` | 移入 `.QuarkMeta/disk_trash`、录制撤销快照、7秒撤销 | 严禁执行物理粉碎与撤销栈清洗 |
| **永久删除（硬删除）** | `PermanentDeleteService` | 模态确认、物理粉碎/覆写、清洗 Undo 历史、抹除数据库 | 严禁录制 Undo 快照、严禁静默删除 |
| **文件读写与传输** | `DiskIoService` | 后台异步执行复制、剪切、粘贴、防重命名覆盖 | 严禁管理 UI 选中状态与右键菜单 |
| **标签与色彩资产** | `TagService` | 维护 `global.db` 标签词典、批量打标与移除 | 严禁包含 Dialog 窗口的绘制 |
| **批量重命名** | `BatchRenameService` | 正则与序列计算、冲突校验、快照一键还原 | 严禁在计算时阻塞 UI 主线程 |
| **预览调度** | `QuickLookService` | 准入白名单过滤、上下文前后文件轮播查找 | 严禁在预览服务里直接物理删除文件 |

---

### 💡 结论（工程口诀）：

**“业务独立成服务，高危可逆分双轨，UI 永远只做薄薄的调用壳。”**

只要坚持这个原则：
1. **UI 控件（如 `ContentPanel`）永远只剩 1 行代码**（只负责触发服务）；
2. **每个服务只负责自己的核心业务闭环**；
3. 未来无论增加多少个快捷键或新窗口，都直接调用现成的服务，系统架构将极其稳固、再也不会腐化。
